# Introducing aint: a static-analysis net for the age of AI-written code

You've handed the keys to an agent. It writes fast, it writes fluently, and it never gets tired of your codebase's conventions. What it doesn't do is pause and ask "wait, should this IAM grant really be `roles/owner`?"

That's the gap `aint` fills.

## The problem nobody's watching for

Agentic coding tools like Claude Code are remarkably good at producing code that *works*. They're optimizing for "the tests pass" and "the feature ships" — not for "this shell command grants project-wide owner access" or "this string that looks like a config value is actually a live API key." A human reviewer might catch these on a slow day. An agent iterating at machine speed, dozens of edits deep into a session, usually won't — and often there's no human in the loop reviewing every diff before it lands.

The failure modes are boring and expensive:
- A `gcloud … add-iam-policy-binding --role=roles/owner` that was meant to be scoped to one bucket.
- A hardcoded API key that seemed reasonable "just for now" and is now in git history forever.
- A `subprocess.run(cmd, shell=True)` that works fine until someone feeds it untrusted input.
- A `chmod 777` that "got it working" and never got revisited.

None of these throw an error. All of them ship clean. That's exactly the problem.

## What aint does

`aint` is a single static Go binary that sits between an agent (or you) and your codebase. It does one thing: it looks at code and shell commands and tells you, in plain language, what's wrong and how to fix it — `file:line:col`, a message, a link to the real explanation.

```
$ aint check .
scripts/deploy.sh:8:1: error [shell-gcp-role-wildcard] granting roles/owner or roles/editor is overscoped; use a narrower predefined or custom role
internal/api/client.go:14:9: error [secret-hardcoded-key] possible hardcoded API key or token
```

What makes it different from "just run a linter":

**It checks shell commands, not just files.** `aint` treats a raw command string exactly like a source file. That means it can statically verify a `gcloud`/`aws`/`kubectl` invocation for overscoping *before* it runs — the same engine, the same checks, no separate IaC toolchain.

**It's wired directly into the agent's loop.** `aint install` drops two hooks into Claude Code's `settings.json`:
- Every `Bash` command is checked *before* it executes. An overscoped grant gets blocked outright — Claude sees the reason and has to fix it, not just get told about it after the fact.
- Every file Claude writes or edits is checked right after, with findings fed back as context for its next turn.

**It's cross-language on day one.** Go, Swift, Python, Node.js, plus shell/IaC and secrets detection that applies to any file — eight checks total at launch, each with its own doc page explaining the "why" and the fix, not just the "what."

**It's configurable, not opinionated.** A `.aint.yaml` lets you tune or disable any check per project, set an ignore list, and control what severity actually fails a CI run. Nothing is mandatory except the checks you keep on.

## Why now

The honest reason: the ratio of "code generated by an agent" to "code reviewed line-by-line by a human" is only going one direction. Tools that assumed a human was always the last line of defense — code review, manual `terraform plan` inspection, "someone will notice" — are running on borrowed time. `aint` isn't trying to replace review. It's trying to catch the specific class of mistake that's cheap to prevent and expensive to discover later, at the exact moment it's about to happen: right before the command runs, right after the file is written.

## What's here today, and what isn't yet

This is a framework release, not a finished product. Today it ships:
- The check engine, config system, and CLI (`aint check`, `aint list`, `aint install`)
- Eight seed checks proving the framework end-to-end across secrets, shell/IaC, and four languages
- Full Claude Code hook integration

What's explicitly *not* here yet, by design: real AST-based parsing (today's checks are fast, regex-based, and honest about that tradeoff), a broader check catalog per language, and real Terraform/Kubernetes-aware IaC analysis beyond shell-command pattern matching. The architecture is built for all of that to slot in without a rewrite — that's next.

## Try it

```bash
go build -o aint ./cmd/aint
./aint check .
./aint install   # wire it into Claude Code
```

If you're pointing an agent at your codebase — and at this point, who isn't — put something between it and the parts of your infrastructure that don't forgive mistakes.
